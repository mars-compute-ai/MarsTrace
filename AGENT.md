# Agent Instructions

These instructions are for changing the harness. An agent that uses the harness to trace
a kernel loads the skills in `skills/` instead.

## Repository Layout

- `xtrace_harness/`: the `xtrace` command: the job manifest and its translation into the
  platform API (`job.py`), cubins and compiler caches (`binary.py`), safetensors files
  (`tensors.py`), the Control Plane client (`client.py`), the operations the commands
  share (`workflow.py`), the stdio MCP server (`mcp.py`) and the commands (`cli.py`).
- `xtrace_harness/viewer/`: `xtrace show`, generated by the maintainers' tooling.
- `xtrace_harness/schemas/`: the platform's JSON Schemas, vendored by
  `scripts/sync_schemas.py`.
- `skills/`: the skills users install; `.claude-plugin/` and `.mcp.json` package them
  with the MCP server for Claude Code.
- `docs/protocol.md`: the mapping from `xtrace.toml` onto the platform API.
- `examples/`, `tests/`.

## Conventions

Every change follows the house conventions of github.com/zobinHuang/humanize: the
Python, README and git conventions apply here. Commit messages are one line in
Conventional Commits form, with no agent attribution.

## Project-Specific Constraints

- **The harness carries no tracing implementation.** It ships to users, so it holds no
  instrumentation or scheduling logic, names no internal tool, and has no text that
  describes how tracing works on the platform. Execution stays on the platform.
- **Code reaches the platform only through `[workspace]`.** Its `source` and `files` are
  what the user shares with the agent on the GPU host, on purpose; do not add another
  path that carries code to execute.
- **The viewer is generated.** Do not edit `xtrace_harness/viewer/`; the maintainers
  regenerate it, and a hand edit is overwritten.
- **The platform's contracts are the source of truth.** The API is defined in
  mars-compute-ai/marscompute-maas, `packages/contracts` (`xtrace.ts`,
  `xtrace-launch-manifest.ts`), and agent mode in `docs/reference/xtrace-agent.md`. A
  change there changes the client, `job.py`, the fake Control Plane in `tests/` and
  `docs/protocol.md` together; refresh the vendored schemas with `scripts/sync_schemas.py`
  and keep `--check` clean.
- **Tests never call the platform.** They use the fake Control Plane in
  `tests/fake_control_plane.py`, which validates every request, and the documents it
  serves, against the vendored schemas, and the fixtures in `tests/fixtures/`.

## Verification

```bash
pip install -e '.[test]'
python -m unittest discover -s tests
ruff check .
python scripts/sync_schemas.py <maas checkout> --check
```

`examples/matmul/matmul.cubin` is built from `examples/matmul/src/matmul.cu` with the
command in its `xtrace.toml`; the tests copy it into every job they build.
